Qwen3.8-27B em 16GB de VRAM: a configuração llama.cpp que funciona

Hardware ·Bruno Pimentel ·18 ago 2026 ·10 min de leitura

Um modelo de 27B parâmetros denso numa placa de 16GB, 100% na GPU, sem ficar trocando teto de contexto por qualidade às cegas. Este guia mostra a matemática da VRAM (GB medidos, não estimados), as três quants que cabem, o comando pronto do llama-server e as alavancas — KV cache quantizado e speculative decoding n-gram — que a comunidade está usando para extrair o máximo de cada GB.

A resposta rápida

Sim, o Qwen3.8-27B roda em 16GB de VRAM. A combinação que a comunidade convergiu após o lançamento (14/08/2026): quantização IQ4_XS (15,71 GB medidos no Hugging Face) para qualidade máxima que cabe inteira, ou UD-Q3_K_XL (13,44 GB) quando o contexto importa mais. Comando mínimo:

llama-server -hf unsloth/Qwen3.8-27B-GGUF:IQ4_XS \
  --ctx-size 16384 --n-gpu-layers 99 \
  --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on \
  --spec-type ngram-simple

Em uma RTX 4070 Ti Super, espere ~20 t/s de geração — mais com speculative decoding em cargas repetitivas (código). Se o seu caso de uso é agêntico com contexto de 64K+, troque a quant para UD-Q3_K_XL e o --ctx-size para 65536.

A matemática dos 16GB: pesos + contexto + CUDA

Os "16GB" do rótulo da placa não são 16GB úteis. O orçamento real de VRAM para o modelo se divide assim:

ComponenteVRAM típicaObservação
Desktop + drivers + CUDA context0,6–1,2 GBJá ocupados antes do modelo carregar
Pesos do modelo (quant)10,3–15,7 GBDepende da quantização escolhida
KV cache (contexto)0,3–3 GBCresce com --ctx-size; cai pela metade com q8_0
Buffers de compute0,3–0,8 GBSomas, ativações, grafos CUDA
mmproj (visão, opcional)0,93 GBSó se passar imagens; use --no-mmproj para liberar

Some tudo: em uma 4070 Ti Super, o espaço real para pesos fica em ~14,5 GB. É por isso que o Q4_K_M (17,11 GB) não cabe inteiro — e por isso que existe este guia. Dois fatores jogam a favor do Qwen3.8-27B:

  • Arquitetura híbrida: só 1 em cada 4 blocos usa atenção completa (o resto é Gated DeltaNet linear, sem KV cache clássico). O custo de contexto por token é muito menor que o de um transformer denso tradicional de 27B.
  • Gama de quants da Unsloth: o repositório GGUF oficial cobre de UD-IQ2_M (10,32 GB) a Q8_0 (29,05 GB) — sempre há um ponto que encaixa no seu orçamento. A tabela completa de tamanhos está no nosso guia de quantização GGUF.

As quants que cabem: tabela com GB medidos

Medições ao vivo via Hugging Face API (18/08/2026) do repositório unsloth/Qwen3.8-27B-GGUF, mais a retenção de qualidade medida pela comunidade (benchmark de perplexidade KL divulgado no r/LocalLLM em 18/08):

QuantizaçãoTamanho (medido)Qualidade retidaCabe em 16GB?
UD-IQ2_M10,32 GB~92–93%Sim, com folga (contexto 128K+)
UD-Q2_K_XL10,68 GB~93%Sim, com folga
UD-Q3_K_XL13,44 GB97,8%Sim — sobra ~1–1,5 GB para contexto
IQ4_XS15,71 GB98,5%Sim, no limite — contexto 8–16K
Q4_K_M17,11 GB~99%Não inteiro — exige offload parcial ou RAM

Fontes: tamanhos medidos via HF API (18/08/2026); retenção de qualidade do benchmark da comunidade r/LocalLLM ("I benchmarked every Qwen 3.8 27B quant that fits in 16GB VRAM", 18/08/2026 — IQ4_XS 98,5%, UD-Q3_K_XL 97,8%, ppl KL 7,0615 vs 7,1113).

Como ler a tabela: a diferença de qualidade entre IQ4_XS e UD-Q3_K_XL é pequena (98,5% vs 97,8%), mas a diferença de espaço é 2,27 GB — que em 16GB é o equivalente a dezenas de milhares de tokens de contexto. A decisão é sempre qualidade máxima vs. contexto máximo, e a arquitetura híbrida do modelo torna o contexto surpreendentemente barato. E se o seu uso é majoritariamente em português: por que o 3-bit dói mais em português.
Cuidado com o mmproj: o encoder de visão (0,93 GB) é baixado automaticamente pelo -hf. Se você não vai passar imagens para o modelo, adicione --no-mmproj e recupere quase 1 GB — em 16GB, isso é o contexto inteiro de uma sessão.

Comandos prontos do llama-server

Três presets testados contra a matemática acima. Todos assumem build atual do llama.cpp (as flags de speculative decoding e KV cache quantizado exigem versão recente) e CUDA para NVIDIA:

Preset A — Máxima qualidade que cabe inteira (IQ4_XS)

llama-server -hf unsloth/Qwen3.8-27B-GGUF:IQ4_XS \
  --ctx-size 16384 --n-gpu-layers 99 \
  --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on \
  --spec-type ngram-simple --no-mmproj \
  --temp 1.0 --top-p 0.95 --top-k 20

15,71 GB de pesos + ~1 GB de sistema deixam pouco mais de 1 GB de margem — com KV q8_0, isso comporta o --ctx-size 16384 com folga. Ideal para chat geral e código com arquivos pontuais. Os parâmetros de sampling são os recomendados pela Qwen para o modo thinking.

Preset B — Contexto longo para código agêntico (UD-Q3_K_XL)

llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q3_K_XL \
  --ctx-size 65536 --n-gpu-layers 99 \
  --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on \
  --spec-type ngram-simple --no-mmproj \
  --temp 1.0 --top-p 0.95 --top-k 20

13,44 GB de pesos abrem ~2,5 GB para o KV cache — o suficiente para 64K de contexto quantizado, o formato de trabalho que usuários de coding agents reportaram em threads do r/LocalLLaMA após empurrar 1M+ de tokens pelo modelo (73K alocados em 16GB com Q4_K_M e técnica de offload parcial). Se o seu agente lê repositórios inteiros, é este preset.

Preset C — Q4_K_M com offload parcial (para quem insiste no Q4)

llama-server -hf unsloth/Qwen3.8-27B-GGUF:Q4_K_M \
  --ctx-size 32768 --n-gpu-layers 54 \
  --cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on \
  --spec-type ngram-simple --no-mmproj

O Q4_K_M (17,11 GB) não cabe inteiro. A saída da comunidade: descarregar ~10 das 64 camadas para a RAM do sistema (--n-gpu-layers 54 ajuste fino no seu setup). Você mantém ~20 t/s porque as camadas restantes na CPU são as mais baratas — mas espere queda em prompt processing. Comece em 54 e suba até a VRAM estourar; recue 2 camadas.

Alavanca 1: KV cache quantizado (dobre seu contexto)

O KV cache padrão é f16. O llama.cpp permite quantizá-lo para q8_0 — metade do tamanho, perda imperceptível:

--cache-type-k q8_0 --cache-type-v q8_0 --flash-attn on

Três pontos que o README oficial do llama.cpp deixa claro e que ninguém conta em tutorial:

  • V quantizado exige flash attention. Sem --flash-attn on (ou o modo auto ativando), o --cache-type-v não funciona — por isso as duas flags andam sempre juntas.
  • K e V aceitam tipos diferentes (ex.: K em q8_0, V em q4_0). Se precisar espremer mais contexto, K aguenta q8_0 e V q4_0 com degradação ainda pequena.
  • Valores aceitos: f32, f16, bf16, q8_0, q4_0, q4_1, iq4_nl, q5_0, q5_1 — para K e V, no modelo principal e no drafter (-ctkd/-ctvd).

Na prática: dobra o contexto disponível sem tocar na quantização do modelo. É a primeira alavanca a puxar antes de descer de IQ4_XS para Q3.

Alavanca 2: speculative decoding n-gram (velocidade grátis)

Speculative decoding clássico usa um modelo drafter menor propondo tokens que o modelo grande valida. Custo: um GGUF extra na VRAM — que em 16GB você não tem. A alternativa do llama.cpp atual, e o motivo dos guias "100% VRAM offload + n-gram" em destaque no r/LocalLLaMA:

--spec-type ngram-simple

Sem drafter, sem VRAM extra. O mecanismo indexa n-grams do próprio prompt e do cache gerado e os usa como rascunho — o modelo principal só valida. Onde brilha:

  • Código: repetição de padrões (imports, boilerplate, fechamento de blocos) faz a taxa de aceitação subir muito. É a carga onde a comunidade reporta os maiores ganhos.
  • Textos estruturados: JSON, YAML, markdown tabular.
  • Prosa criativa livre: ganho pequeno ou nulo — rascunhos são rejeitados e o custo do chute morre no validador.

Variantes disponíveis no --spec-type: ngram-simple (N=12 de lookup, M=48 de draft — padrões ajustáveis via --spec-ngram-simple-size-n/-size-m), ngram-map-k, ngram-map-k4v, ngram-mod, ngram-cache. Se você não quer experimentar, comece no ngram-simple padrão — é o que os guias da comunidade usam.

Referência de ganho: o modelo vizinho Muse Glimmer 30B com drafter dedicado (DFlash, 1,63 GB) chega a 3,1× na RTX 5090. N-gram não chega lá, mas é o único speculative decoding que custa zero GB — em 16GB, "de graça e 1,3–2× em código" ganha de "caro e 3×".

O que esperar em t/s (números reais)

Throughput depende de quant, contexto ocupado e geração de prompt — mas estes são os números publicados pela comunidade nas primeiras 96h após o lançamento dos pesos, para GPU de 16GB com 100% de offload:

Setup (GPU 16GB)QuantContexto alocadoGeração
RTX 4070 Ti SuperQ4_K_M (offload parcial)130K~20 t/s
RTX 4070 Ti SuperIQ4_XS / UD-Q3_K_XL (100% GPU)16K–64K~20–25 t/s + boost n-gram
2× RTX 5060 Ti (32GB)Q4_K_M inteiro32K+~25–30 t/s

Fontes: threads do r/LocalLLaMA e r/LocalLLM de 15–18/08/2026 (links na seção de fontes do portal). Números de comunidade, não medições de laboratório — trate como ordem de grandeza e meça no seu hardware.

Para referência de teto: no Strix Halo (Radeon 8060S, 128GB unificados) medimos 10,6 tok/s no Q5_K_M via Ollama/Vulkan — GPU dedicada de 16GB bate esse número com metade do modelo em bits. E o t/s cai conforme o contexto enche: com 60K+ de tokens em cache, espere queda de 20–30% na geração.

Erros comuns e como resolver

  • "CUDA error: out of memory" no carregamento: a quant não cabe. Desça um nível (Q4_K_M → IQ4_XS → UD-Q3_K_XL) ou reduza --n-gpu-layers. Cada camada retirada devolve ~0,2 GB.
  • Estoura a VRAM depois de minutos de uso: é o KV cache crescendo com o contexto. Diminua o --ctx-size ou quantize o cache (q8_0). Lembre que --ctx-size aloca o máximo no boot — não é um teto flexível.
  • Velocidade caiu muito com contexto cheio: normal (atenção sobre mais tokens). Se for crítico, prefere preset B com Q3 e mais margem de cache.
  • Flag não reconhecida (--spec-type, --cache-type-v): build antigo do llama.cpp. Reconstrua da master — speculative decoding n-gram e V-quant exigem versão recente.
  • Qualidade estranha em português: confira se está no sampling recomendado (temp 1,0 / top-p 0,95 / top-k 20 para thinking; temp 0,7 / top-p 0,80 para instruct). Não é a quant.

Perguntas frequentes

O Qwen3.8-27B roda em 16GB de VRAM?

Sim. IQ4_XS (15,71 GB) cabe inteiro com contexto curto; UD-Q3_K_XL (13,44 GB) cabe com 64K+ de contexto; Q4_K_M (17,11 GB) exige offload parcial de ~10 camadas para a RAM. Todos com ~20 t/s numa 4070 Ti Super.

Qual quantização escolher para 16GB?

IQ4_XS para máxima qualidade que cabe inteira (98,5% de retenção); UD-Q3_K_XL (97,8%) quando contexto longo para agentes importa mais que o último meio ponto de qualidade; Q4_K_M só com offload parcial.

Quantos tokens/s em 16GB?

~20 t/s de geração com Q4_K_M e 130K alocados na RTX 4070 Ti Super (relato da comunidade). Com 100% na GPU em IQ4_XS/Q3 e speculative decoding n-gram em código, espere 20–25 t/s com picos acima.

O que é speculative decoding n-gram?

Aceleração sem modelo drafter: o llama.cpp propõe rascunhos a partir de n-grams do próprio prompt/cache e o modelo só valida. Zero VRAM extra, ganho real em código e texto estruturado. Ative com --spec-type ngram-simple.

Como o contexto cabe junto com o modelo?

Duas coisas: a arquitetura híbrida do Qwen3.8 (só ¼ das camadas usa atenção completa, o KV cache é leve) e a quantização do KV cache para q8_0, que dobra o contexto no mesmo espaço. Sem essas duas, 16GB comportaria muito menos.

Vale a pena 16GB em 2026 ou já troco pra uma de 24GB?

Para o Qwen3.8-27B, 16GB roda bem com as configs deste guia. Mas 24GB (3090 usada, 4090, 5090) elimina o trade-off: Q4_K_XL inteiro + mmproj + 32K de contexto com folga — veja os tiers no guia de hardware.
