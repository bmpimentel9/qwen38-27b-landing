Qwen3.8-27B enxerga: guia de imagem, vídeo e OCR no llama.cpp e Ollama

A resposta rápida (featured snippet)

Para o Qwen3.8-27B enxergar imagens localmente: no llama.cpp, baixe o mmproj junto com o GGUF e suba o servidor com -hf (detecção automática) ou --mmproj arquivo.gguf (manual). No Ollama, a tag qwen3.8:27b já aceita imagens: passe o caminho do arquivo no terminal ou um array images em base64 na API. A visão custa +0,93 GB (BF16) ou +0,63 GB (Q8_0) de VRAM.

# llama.cpp — caminho automático (baixa GGUF + mmproj e detecta sozinho)
llama-server -hf ggml-org/Qwen3.8-27B-GGUF:Q4_K_M

# caminho manual (arquivos já baixados)
llama-server -m Qwen3.8-27B-Q4_K_M.gguf \
  --mmproj mmproj-Qwen3.8-27B-BF16.gguf

# Ollama — a tag padrão já tem entrada Text, Image
ollama run qwen3.8:27b ./foto.png o que aparece nesta imagem?

No terminal do llama.cpp, coloque o caminho da imagem no meio da mensagem; na API, use o formato do model card (image_url / video_url).

VLM nativa: o que o modelo enxerga (e o que o model card promete)

O Qwen3.8-27B não é um LLM de texto que "também aceita" imagem: é uma vision-language model nativa. O Hugging Face classifica o repositório oficial como pipeline_tag: image-text-to-text, e o model card descreve a capacidade como "understands images and videos, from STEM diagrams and documents to hour-scale videos" — de diagramas de STEM e documentos a vídeos na escala de horas. Na arquitetura, é um Causal Language Model with Vision Encoder: a torre de visão nasceu junto com o modelo.

O detalhe que interessa para quem roda local: quase toda a distribuição GGUF do modelo é o cérebro de texto. A visão viaja num arquivo separado e opcional — o mmproj — e quem baixa só o Q4_K_M fica com um modelo cego sem saber. Os números de adoção tornam o gap evidente: 3.561.466 downloads no repositório unsloth/Qwen3.8-27B-GGUF (Hugging Face API, 18/08/2026), contra guias de visão que simplesmente não existiam em português até agora.

Nos benchmarks multimodais do próprio model card, o salto geracional é grande: BabyVision (raciocínio visual geral) foi de 28,9 no Qwen3.6-27B para 85,6 no 3.8 com CI — quase o triplo. Em Vision2Web (desenvolvimento web a partir de screenshot), 45,0 → 62,9. A tabela completa está na seção de benchmarks multimodais deste guia.

mmproj: os 0,93 GB que ligam os olhos do modelo

O mmproj (multimodal projector) é o encoder de visão do modelo convertido para GGUF: ele transforma pixels em embeddings que o LLM entende. Sem ele carregado, o modelo responde a mensagens com imagem como se nada tivesse sido anexado — comportamento confuso para quem não sabe que falta um arquivo.

Onde encontrar (tamanhos medidos via Hugging Face API em 18/08/2026):

RepositórioArquivoTamanho
ggml-org/Qwen3.8-27B-GGUF (oficial)mmproj-Qwen3.8-27B-BF16.gguf0,93 GB
ggml-org/Qwen3.8-27B-GGUF (oficial)mmproj-Qwen3.8-27B-Q8_0.gguf0,63 GB
unsloth/Qwen3.8-27B-GGUFmmproj-F16.gguf / mmproj-BF16.gguf0,93 GB cada

Três fatos práticos, direto da doc multimodal oficial do llama.cpp (libmtmd):

  • Com -hf, o mmproj é detectado automaticamente quando o repositório tem um — é o caminho sem fricção.
  • Com -m modelo.gguf, você precisa apontar --mmproj arquivo.gguf — sem a flag, fica cego.
  • O mmproj vai para a GPU por padrão (--no-mmproj-offload mantém na CPU, útil quando a VRAM está no limite) e --no-mmproj desliga a visão de vez (economia de VRAM para uso só-texto — usado no nosso guia do 27B em 16GB).

llama.cpp: do download ao primeiro OCR

O suporte multimodal do llama.cpp hoje passa pela libmtmd, exposto em três ferramentas: llama-cli, llama-server (via API OpenAI-compatível /chat/completions) e llama-mtmd-cli (para teste e desenvolvimento). Imagem, áudio e vídeo são entradas suportadas.

1. Servidor com visão (o setup do dia a dia)

# automático: baixa o Q4_K_M (18,97 GB) + mmproj do repo oficial
llama-server -hf ggml-org/Qwen3.8-27B-GGUF:Q4_K_M --ctx-size 32768

# manual: você já tem os arquivos
llama-server -m Qwen3.8-27B-Q4_K_M.gguf \
  --mmproj mmproj-Qwen3.8-27B-BF16.gguf \
  --ctx-size 32768 \
  --temp 1.0 --top-p 0.95 --top-k 20

2. Enviando imagem pela API (formato do model card)

O template oficial de mensagens multimodais do Qwen3.8-27B é OpenAI-style — content vira uma lista com um objeto de imagem e um de texto. O llama-server aceita exatamente esse formato no endpoint compatível:

curl http://localhost:8080/v1/chat/completions -H "Content-Type: application/json" -d '{
  "model": "qwen3.8-27b",
  "messages": [{
    "role": "user",
    "content": [
      { "type": "image_url",
        "image_url": { "url": "file:///caminho/da/nota-fiscal.png" } },
      { "type": "text",
        "text": "Extraia em JSON: emissor, CNPJ, valor total e data de emissão." }
    ]
  }]
}'

É o mesmo shape do exemplo oficial do model card — que demonstra até matemática a partir de diagrama (MathVision, 94,6 com CI). Para URL pública, troque o url por um https://... comum.

3. Teste rápido no terminal

# CLI interativo: o caminho do arquivo dentro da mensagem já resolve
llama-cli -hf ggml-org/Qwen3.8-27B-GGUF:Q4_K_M \
  --ctx-size 16384

Ollama: imagem em um comando

No Ollama não há flag de servidor nem arquivo extra para gerenciar: a visão já vem embutida na tag padrão. A página oficial do modelo na biblioteca lista qwen3.8:latest e qwen3.8:27b com 18 GB, contexto 256K e entrada "Text, Image" (verificado em 18/08/2026) — não existe tag especial de visão para procurar.

# terminal: imagem anexada no próprio comando
ollama run qwen3.8:27b ./foto.png o que aparece nesta imagem?

Pela API (/api/chat), o formato oficial da doc de capabilities/vision é um array images com a imagem em base64 dentro da mensagem do usuário:

# 1. baixe uma imagem de teste
curl -L -o test.jpg "https://upload.wikimedia.org/wikipedia/commons/3/3a/Cat03.jpg"

# 2. codifique
IMG=$(base64 < test.jpg | tr -d '\n')

# 3. envie
curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.8:27b",
  "messages": [{
    "role": "user",
    "content": "O que há nesta imagem? Responda em português.",
    "images": ["'"$IMG"'"]
  }],
  "stream": false
}'
Diferença importante entre as stacks: a biblioteca do Ollama lista entrada Text, Image para a qwen3.8 — vídeo não aparece. Para vídeo local, o caminho hoje é o llama.cpp (seção abaixo). E lembre do preço do raciocínio: visão + xhigh de fábrica multiplica tokens de thinking por imagem; o controle de reasoning está no nosso guia de configuração de reasoning (use think: false no Ollama ou --reasoning off para OCR em lote).

OCR e documentos: substitui uma API de OCR?

Para texto nascido digital (PDF de texto, PNG de nota fiscal, screenshot de tabela), sim — com ressalva de velocidade. Os números do model card posicionam o modelo como leitor de documentos de primeira linha:

  • OmniDocBench 1.5 (document intelligence): 91,1 — à frente do Qwen3.6-27B (89,4) e do Opus 4.6 Max (86,6).
  • CharXiv RQ (gráficos científicos): 90,2 com CI (83,7 sem) — leitura de eixos, legendas e conclusões de gráficos.
  • MathVision (matemática a partir de imagem): 94,6 com CI (90,0 sem) — o caso demonstrado no próprio model card com um diagrama geométrico.

A vantagem sobre OCR tradicional não é extrair caracteres — é entender o documento: "qual item da tabela saiu mais caro?", "qual trecho contradiz o contrato?", "gere o JSON dessa fatura". Um OCR devolve texto; o Qwen3.8-27B devolve resposta. Para processamento em lote de milhares de páginas escaneadas, uma ferramenta dedicada de OCR antes do LLM continua sendo o pipeline mais barato — o modelo brilha no documento que exige interpretação, não digitação.

Receita de extração estruturada: peça explicitamente o formato ("Extraia em JSON com as chaves X, Y, Z"). Com --reasoning off e temperatura baixa, a extração fica mais rápida e mais determinística; com thinking ligado, documentos ambíguos rendem melhor. O meio-termo é --reasoning-effort medium.

Bounding boxes: o teste do pelicano do Simon Willison

O teste de visão mais citado do lançamento veio da review hands-on de Simon Willison (16/08/2026): pedir bounding boxes de objetos numa foto, em escala 0-1000. O prompt: "Return JSON bounding boxes for the pelicans in this photo, 0-1000 scale for each dimension".

A resposta — duas caixas com bbox_2d apontando cada pelicano — levou ao veredito "This is such a good match":

[
  { "bbox_2d": [195, 290, 370, 780], "label": "pelicans" },
  { "bbox_2d": [445, 320, 675, 850], "label": "pelicans" }
]

Por que isso importa para uso local: bounding box em JSON é a base de pipelines de detecção barata — etiquetar imagens, pré-anotar datasets, verificar se um objeto aparece num print. O Simon foi além e pediu ao próprio modelo (no modo agêntico) para construir uma ferramenta HTML que renderiza essas caixas sobre a imagem — a ferramenta virou a bbox-lab. O mesmo prompt funciona em português no seu llama-server local.

Dica prática: os valores são normalizados 0-1000, não pixels — divida por 1000 e multiplique pelas dimensões reais da imagem antes de desenhar a caixa.

Vídeo: de clipes curtos a uma hora de gravação

O model card promete hour-scale videos e o formato oficial de envio é o video_url (análogo ao image_url), com uma pegadinha documentada: por padrão o processador faz sampling conservador de frames para não estourar o contexto. A recomendação oficial para vídeos longos é editar o video_preprocessor_config.json:

{ "longest_edge": 469762048, "shortest_edge": 4096 }

O valor corresponde a 224k video tokens e habilita sampling com mais frames — é o que destrava o desempenho em gravações de uma hora (o arquivo video_preprocessor_config.json acompanha o repositório oficial). No vLLM, o sampling é controlável por requisição via extra_body.mm_processor_kwargs com fps (default fps=2); o model card observa que esse controle por requisição é suportado no vLLM.

No llama.cpp, o vídeo entra pelo mesmo caminho da imagem — a doc multimodal lista vídeo como modalidade suportada na libmtmd (arquivo local no CLI, video_url na API). A conta de contexto é a restrição real: cada frame consumido vira token, então vídeo longo + contexto curto = corte silencioso do começo. Para sessões sérias de vídeo, suba o --ctx-size (64K+).

Quanto custa a visão em VRAM

Os pesos do encoder (mmproj) são pequenos; a conta real soma três coisas: quantização do modelo de texto + mmproj + tokens da imagem no KV cache. Referências medidas (tabela completa no nosso guia de quantização GGUF):

SetupModelo textommprojTotal de pesosGPU confortável
Q4_K_M + BF16 (oficial ggml-org)18,97 GB (repo) / 17,11 GB (unsloth)0,93 GB~18-19,9 GB24 GB
Q4_K_M + mmproj Q8_0 (oficial)18,97 GB (repo)0,63 GB~19,6 GB24 GB
UD-Q4_K_XL (unsloth) + BF1617,92 GB0,93 GB~18,9 GB24 GB
IQ4_XS (unsloth) + BF1615,71 GB0,93 GB~16,6 GBnão cabe em 16 GB com folga de KV

A leitura prática: em 16 GB, imagem pontual dá para tentar com mmproj na CPU (--no-mmproj-offload) e contexto curto; o conforto começa em 24 GB. Vídeo é território de 24 GB+ ou memória unificada grande (Strix Halo, Mac 36 GB+) por causa do contexto. Contexto recomendado: 16-32K para OCR e imagens simples, 64K+ para vídeo.

Erros comuns e como resolver

  • "O modelo ignora a imagem que enviei" — mmproj não carregado. Com -m você esqueceu o --mmproj; com -hf, atualize o llama.cpp (builds antigos não têm libmtmd para o Qwen3.8). Confira no log de inicialização a linha do multimodal projector.
  • "CUDA out of memory ao carregar" — some 0,93 GB à sua conta de VRAM (ou use o mmproj Q8_0 de 0,63 GB do repo oficial; ou --no-mmproj-offload para deixar o encoder na CPU).
  • "A resposta vem em inglês" — o encoder é treinado multilíngue, mas o prompt manda: peça explicitamente "responda em português" ou fixe o idioma no system prompt.
  • "Ocr demora uma eternidade" — é o xhigh-trap multiplicado por tokens de imagem. --reasoning off (llama.cpp) ou "think": false (Ollama) resolve a maioria dos casos de extração; contextos acima de 16K ajudam.
  • "Vídeo corta o começo / responde só do fim" — contexto curto para o número de frames: suba o --ctx-size ou reduza o fps do sampling; para hora de vídeo, ajuste o video_preprocessor_config.json conforme o README.
  • "Bounding box errada no desenho" — os valores são escala 0-1000, não pixels: normalize antes de renderizar (foi exatamente o que a bbox-lab do Simon fez).

Perguntas frequentes

O Qwen3.8-27B enxerga imagens?

Sim — é uma VLM nativa (pipeline_tag: image-text-to-text): a torre de visão faz parte do modelo. Localmente, falta só o mmproj (~0,93 GB BF16 / 0,63 GB Q8_0), que o llama.cpp carrega com --mmproj ou detecta com -hf; no Ollama a tag qwen3.8:27b já aceita imagem.

Quanto de VRAM extra a visão consome?

+0,93 GB (BF16) ou +0,63 GB (Q8_0) de pesos, mais os tokens da imagem no contexto. Em 24 GB sobra folga; em 16 GB use --no-mmproj-offload e contexto curto. A tabela completa está no guia de quantização.

O Qwen3.8-27B serve para OCR?

Serve: 91,1 no OmniDocBench 1.5 e 90,2 no CharXiv RQ (model card). A vantagem é entender o documento (responder perguntas, gerar JSON), não só digitar texto — para lote de páginas escaneadas, OCR dedicado antes do LLM continua mais barato.

Como enviar imagem no Ollama?

No terminal, o caminho do arquivo na mensagem (ollama run qwen3.8:27b ./foto.png descreva); na API, array "images" com base64 dentro da mensagem do usuário — formato da doc oficial capabilities/vision.

Ele entende vídeo localmente?

No llama.cpp, sim — vídeo é modalidade suportada na libmtmd, enviada como video_url na API, e o model card cobre vídeos de até escala de hora (com o ajuste do video_preprocessor_config.json). No Ollama a página do modelo lista apenas Text, Image (18/08/2026).

Quais benchmarks multimodais devo citar?

OmniDocBench 91,1 (documentos), MathVision 94,6 com CI (matemática visual), CharXiv 90,2 (gráficos) e Vision2Web 62,9 (web por screenshot) — todos do model card oficial, com comparativos contra Qwen3.6-27B na tabela deste guia.
