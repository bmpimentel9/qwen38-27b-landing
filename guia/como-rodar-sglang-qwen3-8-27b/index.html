Como rodar o Qwen3.8-27B no SGLang (FP8 oficial)

Ollama resolve para o uso pessoal, mas quando o Qwen3.8-27B vira infraestrutura — API para o seu agente, para o time, para o produto — a pergunta muda de "roda?" para "quantos tokens por segundo?". Este guia monta o caminho de máximo throughput em GPU única: o servidor SGLang com o checkpoint FP8 quantizado pela própria Qwen, do pip install ao benchmark de validação.

Por que SGLang + FP8 para o Qwen3.8-27B

O checkpoint FP8 oficial é a resposta da Qwen para quem quer servir o modelo em produção sem pagar o preço do BF16: quantização fine-grained com blocos de 128, com métricas "quase idênticas às do modelo original" — a frase é do próprio model card. Ele pesa 30,89 GB (soma dos arquivos safetensors, medida via HF API), contra ~54 GB do BF16.

O SGLang é um dos três motores de serving que a Qwen recomenda oficialmente para carga de produção, e mantém um cookbook dedicado ao Qwen3.8-27B com receitas validadas para cada placa — algo que nem todo modelo de pesos abertos tem. Três razões para escolher essa combinação:

  • Throughput de verdade em GPU única. A própria equipe do SGLang mediu o FP8 do Qwen3.8-27B a 206,1 tok/s em uma RTX 5090 — e 38,28 tok/s no DGX Spark. Para comparação, o mesmo modelo em GGUF Q4 no Strix Halo via Ollama entrega na casa de 17 tok/s.
  • MTP vem dentro do checkpoint. A cabeça de Multi-Token Prediction treinada pela Qwen (arquivo mtp.safetensors, 0,48 GB) é aproveitada pelo SGLang via EAGLE — speculative decoding sem baixar um drafter separado.
  • Parsers prontos para o Qwen3.8. O cookbook oficial carrega --reasoning-parser qwen3 --tool-call-parser qwen3_coder em todas as receitas: sem eles, um harness recebe os tool calls como texto cru dentro de <tool_call> e nunca parseia nada.
Cobre um buraco do portal: este é o primeiro artigo sobre SGLang do site. Até ontem, todo o conteúdo de execução local cobria Ollama, llama.cpp e vLLM — o motor que a Qwen lista como recomendação para serving não tinha uma única menção em português por aqui. Este guia corrige isso.

Pré-requisitos de hardware e software

O FP8 não roda em qualquer GPU: a precisão de 8 bits em floating point exige hardware moderno. A tabela do cookbook oficial do SGLang valida o Qwen3.8-27B single-GPU em H200, RTX PRO 6000, RTX 5090 e DGX Spark — nas precisões BF16, FP8 e NVFP4.

GPU32 GB VRAM com FP8RTX 5090 (32 GB) ou RTX PRO 6000 Blackwell — entrada em GPU única. H100/H200 (80 GB) para folga de KV cache e concorrência

Alternativa unificadaDGX SparkCookbook valida a 38,28 tok/s — memória unificada muda o jogo de sizing

Se a sua GPU não está nessa lista, o FP8 provavelmente não é o seu caminho — pule para SGLang × llama.cpp/Ollama ou direto para o guia de 16 GB de VRAM.

Passo 1 — Instalar o SGLang (uv/venv ou Docker)

O caminho recomendado pelo cookbook oficial é um ambiente virtual limpo com uv — evita conflito de dependências CUDA com outros projetos:

# criar e ativar o ambiente (qualquer venv padrão serve)
python3 -m venv sglang-env && source sglang-env/bin/activate

# instalar via uv, como no cookbook oficial do SGLang
pip install --upgrade pip
pip install uv
uv pip install sglang

O pacote sglang no PyPI publica versões com frequência semanal (a 0.5.17 é a mais recente no dia desta publicação) — o README da Qwen recomenda explicitamente "usar as versões mais recentes dos frameworks" para garantir suporte ao Qwen3.8, então uv pip install -U sglang antes de começar não é má ideia.

Alternativa Docker — a imagem oficial dedicada ao modelo:

docker pull lmsysorg/sglang:qwen38-27b

O container já vem com CUDA, FlashInfer e os kernels certos para a arquitetura híbrida (Gated DeltaNet + Gated Attention) do Qwen3.8. Se você prefere não gerenciar ambiente Python, comece por aqui e substitua o comando interno do exemplo Docker pelo sglang serve da seção seguinte.

Passo 2 — Subir o servidor FP8

Um comando serve o modelo. Este é o ponto de partida que este portal recomenda — parsers oficiais, nome curto de modelo e contexto deliberadamente menor que o máximo:

python -m sglang.launch_server \
    --model-path Qwen/Qwen3.8-27B-FP8 \
    --served-model-name qwen3.8-27b \
    --reasoning-parser qwen3 \
    --tool-call-parser qwen3_coder \
    --context-length 131072 \
    --mamba-full-memory-ratio 0.35

A primeira execução baixa os 30,89 GB do checkpoint direto do Hugging Face (login hf auth ou HF_TOKEN se quiser puxar de repositório privado; o Qwen3.8-27B-FP8 é público). Quando o log mostrar o endpoint pronto, a API OpenAI-compatible está em http://localhost:30000/v1 — e há também um endpoint compatível com a API Anthropic em /v1/messages, útil para apontar o Claude Code local.

FlagPor quê
--model-path Qwen/Qwen3.8-27B-FP8O checkpoint FP8 oficial. Sem quantização on-the-fly: os pesos já vêm em FP8 de bloco 128 da Qwen
--served-model-name qwen3.8-27bO nome que aparece em /v1/models. Sem isso, clientes precisam enviar a string "Qwen/Qwen3.8-27B-FP8" inteira — nome curto mantém configs de harness limpas
--reasoning-parser qwen3Casa com o template do Qwen3.8: separa o bloco <think> da resposta final. Vem ligado por padrão no modelo — o parser é o que entrega isso estruturado via API
--tool-call-parser qwen3_coderParseia tool calls do formato Qwen (JSON dentro de <tool_call>). Sem ele, agente não funciona — tool call chega como texto cru
--context-length 131072128K em vez dos 262K nativos: cada token de contexto come VRAM do KV/state pool. Suba para 262144 quando a carga pedir (ver seção de contexto)
--mamba-full-memory-ratio 0.35A flag de sizing que mais importa em modelos GDN híbridos. O default 0.9 superdimensiona o pool do Mamba e engarrafa a concorrência. 0.35 é ponto de partida para carga agêntica típica — o cookbook traz uma calculadora para o seu comprimento médio de requisição
Por que 0.35 no mamba ratio? O cookbook oficial resume: modelos híbridos GDN dividem a memória pós-pesos entre um pool de estado do Mamba (que define o teto de concorrência) e um pool de KV de atenção paginado, e a razão entre eles é o --mamba-full-memory-ratio. O default 0.9 reserva o pior caso — bonito para cargas de contexto curtíssimo, desperdiçado para agentes que mandam 20-30K de contexto por requisição. Meça o seu comprimento médio e calcule; não copie o default.

Passo 3 — Contexto: 262K nativo e 1M com YaRN

O Qwen3.8-27B tem 262.144 tokens de contexto nativos — sem truque, sem flag, é o que o checkpoint suporta de fábrica. Para cargas que passam disso, o README oficial documenta a extensão para 1.000.000 de tokens via YaRN (RoPE scaling), com o comando SGLang:

SGLANG_ALLOW_OVERWRITE_LONGER_CONTEXT_LEN=1 python -m sglang.launch_server ... \
    --json-model-override-args '{"text_config": {"rope_parameters": {
        "mrope_interleaved": true, "mrope_section": [11, 11, 10],
        "rope_type": "yarn", "rope_theta": 10000000,
        "partial_rotary_factor": 0.25, "factor": 4.0,
        "original_max_position_embeddings": 262144}}}' \
    --context-length 1000000

Duas recomendações que vêm do próprio model card: use o YaRN só quando a carga realmente exceder 262K — a implementação é static YaRN e pode degradar textos curtos —; e calibre o factor para o seu teto real (carga típica de 524K? factor: 2.0 em vez de 4.0).

Passo 4 — Testar o endpoint (thinking e instruct)

Smoke test imediato com curl:

curl http://localhost:30000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.8-27b",
    "messages": [{"role": "user", "content": "Explique FP8 em uma frase."}],
    "temperature": 1.0, "top_p": 0.95,
    "max_tokens": 1024
  }'

A resposta vem no formato OpenAI, com o raciocínio separado no campo reasoning_content — o thinking mode é o padrão do modelo. As configurações de sampling recomendadas pelo model card:

  • Thinking (padrão): temperature 1,0 · top_p 0,95 · top_k 20
  • Instruct (sem raciocínio): temperature 0,7 · top_p 0,80 · presence_penalty 1,5 · top_k 20

Para uma resposta direta sem o bloco de raciocínio, desligue o thinking na requisição:

"extra_body": { "chat_template_kwargs": { "enable_thinking": false } }

E se a conversa acumula blocos <think> de mensagens antigas pesando no contexto, o preserve_thinking (que vem ligado por padrão e é ótimo para agentes) pode ser desligado por requisição com "preserve_thinking": false — ambos documentados no README do checkpoint.

Passo 5 — MTP: speculative decoding sem baixar nada extra

O Qwen3.8-27B foi treinado com Multi-Token Prediction — e o checkpoint FP8 inclui a cabeça MTP no próprio pacote (é o arquivo mtp.safetensors de 0,48 GB). No SGLang, isso vira speculative decoding via EAGLE com quatro flags:

python -m sglang.launch_server \
    --model-path Qwen/Qwen3.8-27B-FP8 \
    --served-model-name qwen3.8-27b \
    --reasoning-parser qwen3 \
    --tool-call-parser qwen3_coder \
    --speculative-algorithm EAGLE \
    --speculative-num-steps 3 \
    --speculative-eagle-topk 1 \
    --speculative-num-draft-tokens 4

Essa é a configuração 3/1/4 que o cookbook oficial valida por placa. O ganho: em vez de gerar um token por passo, o modelo rascunha 4 com a cabeça MTP e verifica em bloco — onde a aceitação é alta, o decode acelera de forma expressiva. Dois avisos honestos do próprio cookbook: meça — com speculative decoding, precisão mais alta às vezes vence (FP8 + EAGLE: 106,3 tok/s contra 116,1 em um dos cenários medidos) —; e o MTP consome VRAM extra de rascunho, o que em placas de 32 GB pode pedir --mem-fraction-static mais conservador.

Passo 6 — Benchmark de validação

Não confie em número de blog (nem deste): rode o benchmark oficial do SGLang contra o seu servidor e veja os seus tok/s. O bench_serving mede throughput, TTFT e latência entre tokens:

# com o servidor rodando em outro terminal
python3 -m sglang.bench_serving \
    --backend sglang \
    --host 127.0.0.1 --port 30000 \
    --dataset-name random \
    --random-input-len 4096 \
    --random-output-len 1024 \
    --num-prompts 200 \
    --model qwen3.8-27b

Ajuste os parâmetros à sua carga real: --random-input-len perto do seu contexto médio de agente, --max-concurrency no nível de paralelismo que a aplicação usa, --num-prompts para uma amostra estatística decente. Compare três configurações antes de congelar o setup:

CenárioO que isola
input 2048 / output 1024 / conc 1Decode puro em uso interativo — o teto de tok/s de usuário único
input 16384 / output 2048 / conc 4-8Carga agêntica realista — onde o mamba ratio certo aparece
mesma carga ± MTP (EAGLE 3/1/4)O ganho (ou prejuízo) do speculative decoding no SEU contexto
mesma carga ± --chunked-prefill-size 2048Chunks de prefill menores suavizam a latência entre tokens sob carga mista

Referências para calibrar expectativa: 206,1 tok/s FP8 na RTX 5090 e 38,28 tok/s no DGX Spark, números divulgados pela equipe do SGLang na estreia do checkpoint.

Sobre a qualidade do FP8: o model card da Qwen afirma métricas "quase idênticas" ao BF16, mas não publica a tabela comparativa por benchmark. Se a sua aplicação é sensível a qualidade (avaliação, juiz de LLM, extração estruturada), valide: rode o bench_serving com MTP ligado e desligado e uma avaliação qualitativa nos seus prompts reais antes de congelar.

O detalhe que costuma decidir: SGLang exige GPU NVIDIA dedicada com FP8 (Ada/Blackwell ou datacenter) e Linux como plataforma primária. No resto do espectro — memória unificada, iGPU AMD, Mac — o ecossistema GGUF/llama.cpp é o caminho, e o portal tem os guias: como rodar localmente cobre Ollama, llama.cpp, vLLM e MLX.

Troubleshooting: as 4 armadilhas

  • Throughput muito abaixo do esperado sem erro nenhum. Suspeito nº 1: o --mamba-full-memory-ratio no default 0.9. Ele reserva pool Mamba para o pior caso e silenciosamente limita a concorrência — o modelo serve, mas engarrafa. Calcule o ratio para o seu comprimento médio de requisição (o cookbook do SGLang tem a calculadora) e meça de novo.
  • Latência entre tokens irregular sob carga mista. Chunks de prefill de 8192 tokens stallam o decode ~600 ms por vez em modelos GDN híbridos. --chunked-prefill-size 2048 suaviza o ITL e ainda melhora o TTFT de onda única.
  • Agente não consegue chamar ferramentas. Faltou o --tool-call-parser qwen3_coder (ou apontar o harness para o endpoint certo). Sem o parser, o JSON do tool call chega como texto dentro de <tool_call> e nunca parseia. E lembre que o nome do modelo no cliente deve bater com --served-model-name.
  • OOM na GPU de 32 GB com contexto grande. 30,89 GB de pesos deixam pouco para KV/state pool. Três saídas na ordem: baixar --context-length (128K em vez de 262K), reduzir --mem-fraction-static, ou aceitar que a sua carga pede o NVFP4 (24,6 GiB) ou o GGUF 4 bits.

Perguntas frequentes

Como rodar o Qwen3.8-27B no SGLang?

Instale o SGLang (uv pip install sglang), aponte o servidor para o checkpoint Qwen/Qwen3.8-27B-FP8 e use os parsers qwen3: python -m sglang.launch_server --model-path Qwen/Qwen3.8-27B-FP8 --reasoning-parser qwen3 --tool-call-parser qwen3_coder. O servidor expõe API OpenAI-compatible na porta 30000.

Quanto de VRAM precisa o Qwen3.8-27B FP8?

O checkpoint FP8 pesa 30,89 GB (medido via HF API), então o ponto de entrada em GPU única é 32 GB — RTX 5090 ou RTX PRO 6000 Blackwell — com margem apertada para KV cache; o conforto é em H100/H200 de 80 GB. Em 24 GB, o caminho é o GGUF 4 bits via llama.cpp.

Qual a diferença entre FP8 oficial e quantização GGUF?

O FP8 oficial é quantizado pela própria Qwen com método fine-grained de bloco 128, com métricas quase idênticas ao modelo original segundo o model card; GGUF é o formato do llama.cpp com quantizações de 2 a 8 bits feitas pela comunidade. FP8 visa serving de alto throughput (SGLang, vLLM); GGUF visa hardware de consumidor e memória unificada.

SGLang ou llama.cpp para o Qwen3.8-27B?

SGLang para GPU NVIDIA dedicada servindo aplicações: throughput alto (206,1 tok/s medidos na RTX 5090), MTP via EAGLE no próprio checkpoint e parsers de reasoning/tool-call nativos. llama.cpp para hardware de consumidor e memória unificada (Strix Halo, Macs): GGUF 4 bits cabe em 17 GB e roda via Ollama com um comando.

Como ativar o MTP no SGLang?

O checkpoint FP8 já traz a cabeça MTP (mtp.safetensors, 0,48 GB) treinada pela Qwen. Ative com: --speculative-algorithm EAGLE --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4 — a configuração recomendada no cookbook oficial do SGLang.

O SGLang funciona com o modo thinking do Qwen3.8?

Sim, e o thinking vem ligado por padrão. O parser --reasoning-parser qwen3 casa com o template que alterna o thinking via enable_thinking. Para resposta direta, envie chat_template_kwargs com enable_thinking: false; para não preservar o raciocínio de mensagens antigas, preserve_thinking: false.
