Configuração de reasoning do Qwen3.8-27B: como desativar o overthinking (e acelerar tudo)

Guias ·Bruno Pimentel ·18 ago 2026 ·12 min de leitura

O modelo sai de fábrica pensando no máximo — e gastando 22.276 tokens de raciocínio para escrever 3.223 de resposta. Este guia mostra como desligar, dosar e acelerar o reasoning no llama.cpp, Ollama e LM Studio, com números reais em hardware de consumidor.

A resposta rápida (featured snippet)

Para desativar o overthinking do Qwen3.8-27B: no llama.cpp, use --reasoning off (desliga por completo) ou --reasoning-budget 0 (encerra o raciocínio imediatamente). Para dosar em vez de desligar, use --reasoning-effort low ou medium. No Ollama, envie "think": false na chamada de API. E para acelerar o que sobrar, ative o MTP com --spec-type draft-mtp.

# llama.cpp — desligar o thinking de vez
llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --reasoning off

# dosar em vez de desligar (recomendado p/ código e agentes)
llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --reasoning-effort medium

# teto de raciocínio em tokens (1.024 tokens de thinking, chega)
llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --reasoning-budget 1024

# acelerar com MTP (o comando que Simon Willison usou no DGX Spark)
llama-server \
  -hf  ggml-org/Qwen3.8-27B-GGUF:Q4_K_M \
  -hfd ggml-org/Qwen3.8-27B-GGUF:Q4_0 \
  --spec-default --spec-type draft-mtp --reasoning-preserve

No Ollama, o controle é um campo da requisição — sem flag de servidor:

curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.8:27b",
  "messages": [{ "role": "user", "content": "Resuma este texto" }],
  "think": false,
  "stream": false
}'

O problema: excelente, mas "wildly overthinking" por padrão

O Qwen3.8-27B chegou em 14/08/2026 com um default polêmico: reasoning_effort = xhigh. A documentação oficial descreve três níveis — xhigh (default) para tarefas complexas, medium para equilíbrio e low para eficiência. O problema é que "complex task" virou o padrão para tudo, inclusive para um pedido de SVG.

A medição mais citada do lançamento é da review hands-on de Simon Willison (16/08/2026), com o veredito que resume o modelo: "excellent, but it defaults to wildly overthinking things". Os números do teste do SVG do pelicano andando de bicicleta:

21 min
tempo total com default xhigh
22.276
tokens de raciocínio
3.223
tokens de resposta (o SVG)
137s
mesmo prompt com reasoning off

São 6,9 tokens de raciocínio para cada token de resposta — e a resposta final saiu em 2 minutos e 17 segundos com o thinking desligado (3.715 tokens). O próprio Simon nota a ironia: o resultado do xhigh foi "de longe o melhor pelican SVG que já consegui com um modelo local", mas "was that worth waiting 21 minutes for? Absolutely not."

Há um agravante prático: com o contexto default de 8.192 tokens do LM Studio, o Qwen enche a janela só pensando antes de escrever qualquer resposta. A discussão #7 do repositório unsloth/Qwen3.5-27B-GGUF documenta o mesmo comportamento na família: um simples "Hi" faz o modelo raciocinar até estourar o contexto — e o fix reportado pela comunidade foi exatamente --reasoning-budget 0 no llama.cpp.

Escala do problema: o GGUF do Qwen3.8-27B passou de 3,5 milhões de downloads em 4 dias (3.561.466 em 18/08, Hugging Face API). É uma base instalada enorme procurando "como desligar o thinking" — e a resposta correta mudou de fórum em fórum nesta semana, porque as flags do llama.cpp também mudaram.

Os 4 controles de reasoning no llama.cpp

O llama.cpp atual expõe quatro flags para governar o thinking (todas documentadas no README oficial do llama-server, verificado em 18/08/2026):

FlagValoresO que faz
--reasoning on / off / auto Liga/desliga o raciocínio no chat. off = resposta direta, zero tokens de thinking.
--reasoning-effort minimal, low, medium, high, xhigh, max ou default Profundidade do raciocínio passada ao template do modelo. default preserva o xhigh de fábrica — é a armadilha.
--reasoning-budget -1 (irrestrito) / 0 (encerra na hora) / N>0 (teto em tokens) Orçamento de tokens para o thinking. 0 é o "mata-bomba"; 1024 deixa o modelo raciocinar um pouco e corta. Aceita --reasoning-budget-message para injetar um aviso quando o teto estoura.
--reasoning-preserve / --no-reasoning-preserve flag on/off Mantém o trace de raciocínio no histórico completo da conversa (não só na última mensagem). Simon manteve ativado no comando com MTP.

Há ainda o --reasoning-format (none / deepseek / deepseek-legacy), que só controla onde o trace aparece na resposta da API (em message.content ou message.reasoning_content) — não economiza token nenhum.

Como desativar o thinking em cada ferramenta

llama.cpp (llama-server / llama-cli)

# desligar
llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --reasoning off

# reduzir
llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --reasoning-effort low

# teto explícito
llama-server -hf unsloth/Qwen3.8-27B-GGUF:UD-Q4_K_XL --reasoning-budget 1024

Ollama

O qwen3.8:27b (18 GB, 256K de contexto) aceita o campo think na API: false para resposta direta ou os níveis low / medium / high / max para dosar. O trace volta em message.thinking; a resposta final em message.content (documentação oficial Ollama, capabilities/thinking).

curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.8:27b",
  "messages": [{ "role": "user", "content": "Sua pergunta" }],
  "think": false
}'

LM Studio

O GGUF da unsloth no LM Studio preserva o default xhigh de fábrica — e o contexto inicial de 8.192 tokens da ferramenta transforma overthinking em erro de contexto. Dois ajustes: suba o contexto (o modelo aguenta 262.144 nativos) e reduza o reasoning effort nas configurações do modelo. Para controle fino (budget em tokens, MTP), o caminho é o llama-server direto.

API OpenAI-compatível (vLLM, provedores)

Servidores que expõem a API OpenAI-compatível repassam o parâmetro reasoning_effort do request. No vLLM, sirva com --reasoning-parser qwen3 (vLLM ≥ 0.27.1) e ajuste o esforço por chamada — o nosso guia de execução cobre o setup completo.

reasoning_effort: xhigh, medium, low ou off?

Não existe resposta única — existe a resposta por tarefa. O modelo foi construído para long-horizon agentic tasks (o model card mostra os maiores saltos justamente aí: DeepSWE +28,9, QwenSWEBench +29,7), então o thinking é ferramenta, não defeito. O defeito é o default:

Caso de usoConfiguração recomendadaPor quê
Chat, escrita, tradução, resumo--reasoning off (ou think: false)Raciocínio não agrega; economiza 10-30× em tokens e minutos.
Dia a dia com código, agentes, tool calling--reasoning-effort mediumO equilíbrio que a própria documentação Qwen recomenda: qualidade mantida sem o custo xhigh.
Matemática pesada, debugging difícil, planejamento longo--reasoning-effort high + --reasoning-budget 4096Aqui o thinking paga o preço — mas com teto, para não repetir o episódio dos 21 minutos.
Batch/automação onde custo importa--reasoning-effort low"Eficiência otimizando por velocidade e custo" (docs Qwen).

Regra prática para hardware de consumidor: comece no medium e só suba quando a resposta vier errada por falta de raciocínio — não o contrário. Descer é barato; subir custa minutos por chamada.

Overthinking × seu hardware: a conta em tok/s

O teste do Simon foi num DGX Spark — máquina cara. A conta abaixo usa throughput medido pelo portal (Strix Halo, Ollama/Vulkan) e relatos da comunidade para mostrar quanto custa o xhigh-trap em hardware que a gente usa no Brasil:

HardwareQuantizaçãoDecode (t/s)22.276 tokens de thinking =
DGX Spark (teste do Simon, 16/08)Q4_K_M~17,7 (efetivo no teste)~21 min
AMD Strix Halo (medição do portal)Q4_K_M17,3~21,4 min
AMD Strix Halo (medição do portal)Q5_K_M10,6~35 min
RTX 3060 12GB (offload parcial, estimado)Q4_K_M15–2515–25 min
RTX 4090 24GB (estimado)Q4_K_M70–904–5 min

A leitura fria: no Strix Halo e em qualquer GPU de faixa média, o default xhigh transforma uma resposta de 2 minutos em meia hora de silêncio — e pode estourar o contexto antes de responder nada. Nas medições do portal, o mesmo 27B no Q4_K_M entrega 17,3 t/s contra 12,4 t/s do Qwen3.6-27B (comparativo completo aqui); com Q5_K_M cai para 10,6 t/s. Cada token de raciocínio custa o mesmo que um token de resposta — só que você não vê os primeiros.

Quanto à memória: a tabela completa de GB por quantização está no nosso guia de quantização GGUF (IQ4_XS = 15,71 GB; Q4_K_M = 17,11 GB). Overthinking também consome KV cache: raciocinar 22 mil tokens em contexto curto é o caminho mais rápido para OOM — quem roda em 16GB deve ler o guia do 27B em 16GB de VRAM junto com este.

MTP: o speedup que já saiu do forno do llama.cpp

Desligar o overthinking corta o desperdício. O MTP (Multi-Token Prediction) ataca o outro lado: a velocidade de cada token. A arquitetura do Qwen3.8 traz camadas MTP embutidas — um mecanismo barato "adivinha" vários tokens à frente e o modelo principal só verifica. O suporte no llama.cpp chegou no PR #22673 (merged em 16/05/2026), então qualquer build atual já tem — é o comando que Simon usou:

llama-server \
  -hf  ggml-org/Qwen3.8-27B-GGUF:Q4_K_M \
  -hfd ggml-org/Qwen3.8-27B-GGUF:Q4_0 \
  --spec-default \
  --spec-type draft-mtp \
  --reasoning-preserve

O detalhe que quase todo mundo erra: o -hfd aponta para o Q4_0 do repositório oficial ggml-org, que preserva as camadas MTP — quant da unsloth sem essas camadas não serve de drafter. O --spec-type aceita draft-mtp, draft-simple, draft-eagle3, ngram-simple e outros; para o Qwen3.8, o draft-mtp é o caminho.

Os números de ganho circulam soltos e parecem contraditórios — não são. Cada um tem seu contexto:

FonteHardware / setupGanho
Simon Willison (16/08, benchmark GPT-5.6/Codex)DGX Spark, llama-server Q4_K_M + draft Q4_0+72% vs LM Studio default
Testes no thread do PR #22673Mesmo GGUF, draft-mtp habilitadodecode 22,97 → 42,45 t/s (~1,85×)
ik_llama.cpp, GGUF RDson IQ4_KSRTX 3090, draft depth 1+16% (28,99 t/s)
tproger.ruQwen3.6-27B Q8_0 (geração anterior)16–22 t/s vs 7 baseline (2,2–2,4×)
Dois avisos honestos: (1) no thread do PR #22673, o prefill ficou mais lento com MTP (~665 vs 1.315 tok/s, ~0,51×) — em prompts longos, parte do ganho do decode se paga no processamento inicial; (2) a taxa de aceitação dos drafts varia com a tarefa (código aceita melhor que texto criativo). MTP não é mágica universal: meça no seu caso de uso.

Combine as duas alavancas e o resultado é grande: reasoning medium corta a maior parte dos tokens desperdiçados e o MTP acelera o que sobra — é a diferença entre "modelo que eu desisti de usar" e "modelo do dia a dia".

Presets prontos por perfil de hardware

GPU 24GB (RTX 3090 / 4090) — qualidade máxima com teto de sanidade

llama-server \
  -hf  ggml-org/Qwen3.8-27B-GGUF:Q4_K_M \
  -hfd ggml-org/Qwen3.8-27B-GGUF:Q4_0 \
  --spec-default --spec-type draft-mtp --reasoning-preserve \
  --reasoning-effort medium \
  --ctx-size 65536 \
  --temp 1.0 --top-p 0.95 --top-k 20

GPU 16GB (4070 Ti Super / 5070 Ti) — cabe, mas sem folga

llama-server \
  -hf unsloth/Qwen3.8-27B-GGUF:IQ4_XS \
  --reasoning-effort medium \
  --reasoning-budget 1024 \
  --spec-type ngram-simple \
  --ctx-size 32768 --flash-attn on \
  --cache-type-k q8_0 --cache-type-v q8_0 \
  --no-mmproj \
  --temp 1.0 --top-p 0.95 --top-k 20

(IQ4_XS = 15,71 GB medidos; KV cache q8_0 e sem o mmproj de visão para sobreviver — detalhes no guia de 16GB.)

Strix Halo / Mac 32GB+ (memória unificada) — conversa longa

llama-server \
  -hf unsloth/Qwen3.8-27B-GGUF:Q4_K_XL \
  --reasoning off \
  --ctx-size 131072 \
  --temp 0.7 --top-p 0.80 \
  --repeat-penalty 1.5

(Com thinking off, use o sampling do modo Instruct: temp 0,7 / top_p 0,80 / repetition_penalty 1,5.)

Ollama — o mínimo viável

ollama run qwen3.8:27b
# e na hora de chamar a API: "think": false

Erros comuns e como resolver

  • "O modelo enche o contexto pensando e falha" — é o xhigh-trap. Suba o contexto e aplique --reasoning-budget 1024 (ou 0 para matar). O relato do "Hi" que estoura o contexto está na discussion #7 da unsloth.
  • "--reasoning-budget não faz nada" — build antigo do llama.cpp. As flags de reasoning/budget estão no README atual; atualize o binário.
  • "Respostas em loop com thinking ligado" — você usou temperature 0. O model card é explícito: thinking exige temp 1,0 / top_p 0,95 / top_k 20; temp 0 entra em loop repetitivo.
  • "MTP não acelera nada / erro no drafter" — o GGUF do draft precisa preservar as camadas MTP: use o Q4_0 do repositório oficial ggml-org no -hfd, não uma quant qualquer da unsloth.
  • "MTP piorou em prompt longo" — o prefill cai ~0,51× no caminho MTP (thread do PR #22673). Para workloads de prompt gigante, meça antes de adotar.
  • "LM Studio trava no início" — contexto de 8.192 default + xhigh = estouro antes da primeira resposta. Suba o contexto e baixe o esforço.

Perguntas frequentes

Desativar o thinking piora a qualidade da resposta?

Em tarefas que exigem raciocínio profundo (matemática, código difícil, planejamento agêntico), sim — o thinking existe por um motivo, e o próprio Simon Willison reconheceu que o melhor SVG saiu com o raciocínio ligado. Mas para chat, escrita e a maioria das tarefas, a diferença não justica o custo: o mesmo prompt com reasoning off entregou em 137 segundos o que o default levou 21 minutos. A recomendação prática é medium como padrão, não off absoluto.

Qual o comando exato para desligar o thinking no llama.cpp?

--reasoning off no llama-server desliga por completo. Alternativas: --reasoning-budget 0 (encerra o raciocínio imediatamente — o fix reportado pela comunidade na discussion #7 da unsloth) e --reasoning-effort low/medium para dosar sem desligar.

O que é o "xhigh-trap" do Qwen3.8-27B?

O modelo sai de fábrica com reasoning_effort = xhigh como padrão — pensamento máximo para qualquer tarefa, até as triviais. No teste mais citado do lançamento, isso significou 22.276 tokens de raciocínio e 21 minutos para um SVG de 3.223 tokens. Como o GGUF da unsloth e o LM Studio preservam esse default, todo usuário novo cai na armadilha sem saber.

O MTP funciona em qualquer GGUF do Qwen3.8-27B?

Não. O draft-mtp precisa de um GGUF que preserve as camadas MTP do modelo — o Q4_0 do repositório oficial ggml-org é o drafter usado no comando testado por Simon Willison. Quants da unsloth sem essas camadas não funcionam como drafter.

Como controlo o thinking no Ollama?

Pelo campo think da API: false para resposta direta ou low/medium/high/max para dosar. O trace de raciocínio volta em message.thinking e a resposta em message.content.

Quais valores de sampling usar com o thinking desligado?

Os do modo Instruct do model card: temp 0,7, top_p 0,80 e repetition_penalty 1,5. Com thinking ligado: temp 1,0, top_p 0,95, top_k 20 — e nunca temperature 0, que faz o modo entrar em loop.
