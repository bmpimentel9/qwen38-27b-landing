Como rodar o Qwen3.8-27B no Ollama — do ollama run ao MTP em produção

Guias ·Bruno Pimentel ·22 ago 2026 ·15 min de leitura

Ollama é a porta de entrada do universo de LLMs locais: um comando e o Qwen3.8-27B está rodando. Mas por trás do ollama run qwen3.8:27b existe um ecossistema de 12 tags, Modelfile customizável com MTP, reasoning effort ajustável por requisição e suporte nativo a visão — e é isso que este guia mapeia, do primeiro pull ao tuning fino de produção.

Por que Ollama para o Qwen3.8-27B?

O Ollama é a ferramenta que a maioria dos usuários de LLM local conhece primeiro. A página da biblioteca oficial do qwen3.8 já acumula 566.2 mil downloads (ago/2026) — é 8,4× mais que as 67.1K registradas no llms.txt do portal há menos de uma semana, sinal de adoção acelerada.

Três razões para começar por aqui:

  • Zero-config. ollama run qwen3.8:27b e o modelo inteiro (18 GB, 256K de contexto, visão) está rodando — sem variáveis de ambiente, sem flags de CUDA, sem compilar kernel.
  • Ecosistema de tags. São 12 variantes que vão do Q4_K_M de 18 GB ao BF16 de 56 GB, incluindo opções com MTP embutido, MLX para Mac e NVFP4 para Blackwell — escolha o que cabe na sua GPU e pronto.
  • API nativa. O servidor embutido do Ollama expõe endpoint OpenAI-compatible, então qualquer app que fala com a OpenAI pode apontar para o seu modelo local trocando a base URL.
Este guia preenche um buraco do portal. Até agora, o Qwen3.8-27B tinha guias para llama.cpp, SGLang, vLLM e LM Studio — mas zero para o motor que é a porta de entrada de 90% dos usuários. A thread de release no r/LocalLLaMA e o megathread mostram dezenas de usuários configurando no Ollama: a demanda estava aqui, o conteúdo não.

A instalação é trivial: acesse ollama.com/download, baixe o instalador do seu sistema, execute. Verifique com:

ollama --version

No Linux, o instalador registra um serviço systemd; no macOS, o app da bandeja fica rodando em segundo plano. Em ambos os casos, a API REST fica disponível em http://localhost:11434.

Variante ROCm (AMD): se você tem GPU AMD no Linux, instale a build ROCm dedicada seguindo as instruções da documentação oficial Ollama + ROCm.

Todas as tags do qwen3.8 no Ollama

A família qwen3.8 na biblioteca Ollama tem 12 tags. Todas compartilham a mesma arquitetura (27B denso, híbrida Gated DeltaNet + Gated Attention) e contexto de 256.000 tokens nativos. A diferença está na quantização e no suporte a MTP:

TagTamanhoQuantMTPMLXIndicado para
qwen3.8:latest (alias de :27b)18 GBQ4_K_MNão—GPU 24 GB, uso geral
qwen3.8:27b18 GBQ4_K_MNão—GPU 24 GB, uso geral
qwen3.8:27b-mtp-q4_K_M18 GBQ4_K_MSim—GPU 24 GB, com aceleração MTP
qwen3.8:27b-mtp-q8_030 GBQ8_0Sim—GPU 32 GB+ (RTX 5090)
qwen3.8:27b-mtp-bf1656 GBBF16Sim—Datacenter (A100/H100 80 GB)
qwen3.8:27b-q4_K_M18 GBQ4_K_MNão—GPU 24 GB (equivalente ao :27b)
qwen3.8:27b-q8_030 GBQ8_0Não—GPU 32 GB+
qwen3.8:27b-bf1656 GBBF16Não—Datacenter
qwen3.8:27b-mlx18 GBQ4_K_M (MLX)—SimMac Apple Silicon 32 GB+
qwen3.8:27b-mlx-bf1656 GBBF16 (MLX)—SimMac 96 GB+ (M3 Ultra, M2 Ultra)
qwen3.8:27b-mxfp832 GBMXFP8 (MLX)—SimMac 48 GB+
qwen3.8:27b-nvfp418 GBNVFP4 (MLX)—SimMac 32 GB+ (Apple Silicon)
Atenção ao MTP: as tags com -mtp- no nome já incluem a cabeça Multi-Token Prediction treinada pela Qwen e trazem draft_num_predict: 4 configurado por padrão nos metadados. Isso significa que o speculative decoding com 4 tokens de rascunho está ativo desde o primeiro ollama run — sem flags extras. As tags sem MTP (a grande maioria, incluindo a :latest) não têm draft_num_predict configurado.

Passo 1 — ollama run qwen3.8:27b

O comando mais simples possível. Baixa o modelo (18 GB na primeira execução) e abre um chat interativo:

ollama run qwen3.8:27b

Pronto. O modelo está rodando com thinking mode ligado (padrão de fábrica), 256K de contexto e temperatura 0.8 (default do Ollama). Dentro do chat interativo, você pode usar comandos /:

# dentro da sessão interativa
>>> /show modelfile      # exibe o Modelfile atual
>>> /set parameter num_ctx 131072   # reduz contexto
>>> /set parameter temperature 0.7   # ajusta temperatura
>>> /set parameter no_think true     # desliga thinking
>>> /clear                           # limpa histórico

Para saída única sem chat interativo (útil para scripts):

ollama run qwen3.8:27b "Explique o que é atenção híbrida em uma frase."

Passo 2 — Modelfile customizado (ctx-size, MTP, GPU)

O Modelfile é o equivalente Ollama ao llama-cli com flags: define parâmetros que persistem entre execuções. O caminho completo para o Qwen3.8-27B com 256K de contexto, parâmetros oficiais do model card e MTP:

# Modelfile — Qwen3.8-27B otimizado
FROM qwen3.8:27b

# Contexto nativo máximo
PARAMETER num_ctx 262144

# Parâmetros de sampling — Thinking mode (model card oficial)
PARAMETER temperature 1.0
PARAMETER top_p 0.95
PARAMETER top_k 20

# Evita repetição conservadora (default Ollama é 1.0 = desligado)
PARAMETER repeat_penalty 1.0
PARAMETER repeat_last_n -1

# Tokens máximos (ilimitado)
PARAMETER num_predict -1

# Seed para reprodutibilidade (opcional; 0 = aleatório)
PARAMETER seed 0

Salve como Modelfile e crie o modelo customizado:

ollama create qwen3.8-27b-custom -f Modelfile

Agora rode com o nome escolhido:

ollama run qwen3.8-27b-custom

Para habilitar MTP no Modelfile, parta da tag MTP em vez da base:

# Modelfile MTP — parte do qwen3.8:27b-mtp-q4_K_M
FROM qwen3.8:27b-mtp-q4_K_M

PARAMETER num_ctx 262144
PARAMETER temperature 1.0
PARAMETER top_p 0.95
PARAMETER top_k 20
# MTP já configurado na tag de origem (draft_num_predict 4)
# Para desligar: PARAMETER draft_num_predict 0

Controle de GPU (num_gpu): o Ollama gerencia automaticamente o offloading de camadas para GPU. Em setups multi-GPU ou para forçar uso máximo da GPU, você pode usar variáveis de ambiente ou o parâmetro num_gpu no Modelfile (disponível em versões recentes do Ollama que expõem os parâmetros do llama.cpp). Na prática, se o Ollama detecta GPU CUDA, ele já usa todas as camadas disponíveis — a flag num_gpu é útil para reservar camadas para CPU em setups com pouca VRAM:

# No Modelfile: carrega só 50 camadas na GPU (de 64)
PARAMETER num_gpu 50

Passo 3 — Reasoning effort e thinking mode

O thinking mode do Qwen3.8-27B vem ligado por padrão — o modelo raciocina passo a passo dentro de um bloco <think> antes de responder. O parâmetro reasoning_effort controla quantos tokens o modelo gasta nesse raciocínio interno. Quatro níveis disponíveis:

NívelComportamentoQuando usar
xhigh (default)Máximo raciocínio — pode gastar 20K+ tokens pensandoMatemática, código complexo, agentes multi-passo
highRaciocínio profundo, mas com limite práticoAnálise, decisões com trade-offs
mediumEquilíbrio entre pensar e responderUso geral, chatbots, perguntas técnicas
lowRaciocínio mínimo, respostas mais diretasExtração de dados, perguntas factuais
desligadoModo Instruct — resposta direta sem bloco <think>Chat rápido, tradução, tarefas simples

No Ollama, o reasoning_effort é controlado via API ou requisição — não há flag direta de CLI para isso. O parâmetro é passado no corpo da requisição como options:

# API — reasoning effort medium
curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.8:27b",
  "messages": [{"role": "user", "content": "O que é MTP?"}],
  "options": {
    "reasoning_effort": "medium"
  }
}'

Para desligar o thinking (modo Instruct) — duas formas:

  • Por requisição (API): "options": { "no_think": true }
  • No Modelfile: PARAMETER no_think true
  • No CLI interativo: /set parameter no_think true
Atenção ao xhigh default: O reasoning_effort xhigh é o padrão de fábrica do modelo — e é caro. Simon Willison documentou que um SVG de 3.223 tokens consumiu 22.276 tokens de raciocínio (21 minutos de geração) com xhigh ligado. Com reasoning off, o mesmo prompt entregou em 137 segundos. Se você está testando o modelo pela primeira vez, comece com low ou desligado — o ganho de velocidade é dramático.

O parâmetro preserve_thinking também é suportado (retém os blocos <think> de mensagens anteriores no contexto), útil para agentes que precisam lembrar o raciocínio de passos anteriores. Desligue com "preserve_thinking": false na API ou Modelfile.

Passo 4 — MTP: Multi-Token Prediction no Ollama

O Multi-Token Prediction (MTP) é uma das inovações do Qwen3.8: o modelo foi treinado para prever múltiplos tokens de saída por passo — não um de cada vez. No Ollama, você tem duas abordagens:

Abordagem A: Tag MTP dedicada (recomendada)

A tag qwen3.8:27b-mtp-q4_K_M já inclui a cabeça MTP treinada pela Qwen (arquivo mtp.safetensors) e o parâmetro draft_num_predict: 4 nos metadados. O speculative decoding com 4 tokens de rascunho está ativo desde o primeiro comando:

# Puxar a tag MTP
ollama pull qwen3.8:27b-mtp-q4_K_M

# Rodar — MTP já ativo
ollama run qwen3.8:27b-mtp-q4_K_M

O ganho esperado é de ~1,5× a 2,5× no decode, variando conforme hardware e conteúdo. No llama.cpp (que o Ollama usa internamente), medições mostram aceleração de até +72% no DGX Spark e ~1,85× (22,97 → 42,45 tok/s) nos testes do PR #22673. A aceitação média do drafter fica entre 0,77 e 0,90 — ou seja, 3 de cada 4 tokens rascunhados são aceitos pelo modelo principal.

Abordagem B: Usar drafter externo

Em vez da cabeça MTP embutida, você pode apontar o Ollama para um drafter GGUF separado para speculative decoding. Esta abordagem não é suportada nativamente pelo ollama run — requer o servidor e configuração extra:

# Iniciar servidor com drafter externo (se disponível)
ollama serve
# Consumir via API com model_extra opções

Na prática, para a maioria dos usuários, a Abordagem A (tag MTP dedicada) é a mais simples e eficaz — a cabeça MTP foi treinada pela própria Qwen especificamente para este modelo, não um drafter genérico.

Verifique se o MTP está ativo: depois de rodar ollama run qwen3.8:27b-mtp-q4_K_M, dentro do chat interativo digite /show modelfile — você deve ver draft_num_predict 4 na saída. Se não aparecer, adicione PARAMETER draft_num_predict 4 no seu Modelfile customizado.

Passo 5 — Visão e multimodalidade

O Qwen3.8-27B é uma VLM nativa — o encoder de visão é parte do modelo, não um adaptador externo. A tag qwen3.8:27b já aceita entrada Text + Image (a biblioteca Ollama lista explicitamente as modalidades suportadas).

No CLI interativo:

ollama run qwen3.8:27b "Descreva esta imagem em detalhes." --image ~/foto.jpg

Via API Python:

import ollama

response = ollama.chat(
    model='qwen3.8:27b',
    messages=[{
        'role': 'user',
        'content': 'Descreva esta imagem',
        'images': ['caminho/para/foto.jpg']
    }]
)
print(response['message']['content'])

Via API REST:

curl http://localhost:11434/api/chat -d '{
  "model": "qwen3.8:27b",
  "messages": [
    {
      "role": "user",
      "content": "O que tem nesta imagem?",
      "images": [""]
    }
  ]
}'

O encoder de visão (mmproj) está embutido no pacote — não há download separado de arquivos .gguf de visão como no llama.cpp. Todas as 12 tags incluem suporte a imagem no mesmo pacote.

Limitação conhecida: a página da biblioteca Ollama lista as modalidades como Text, Image — isto é, não há suporte declarado a vídeo no Ollama (diferente do llama.cpp, que suporta vídeo de até hora com o mesmo modelo). Para tarefas de vídeo, use o guia de visão e vídeo no llama.cpp.

Passo 6 — Flash attention e desempenho

O flash attention é uma técnica que acelera a atenção do transformer reduzindo acessos à memória de alto consumo de banda. No Ollama, o suporte a flash attention vem do backend llama.cpp — e nas versões mais recentes (Ollama 0.5+), o flash attention é habilitado automaticamente quando o hardware suporta (GPUs NVIDIA com CUDA 11.8+).

Você pode verificar se o flash attention está ativo olhando os logs do servidor:

ollama serve 2>&1 | grep -i flash

Se quiser forçar o desligamento (por exemplo, se encontrar degradação em benchmarks raros):

# Desligar flash attention via variável de ambiente
OLLAMA_FLASH_ATTN=0 ollama run qwen3.8:27b

No Qwen3.8-27B, o impacto do flash attention é notável em contextos longos: em 256K de contexto, a atenção plena (não flash) consumiria ~16× mais largura de banda para o mecanismo de atenção (só 16 das 64 camadas são full-attention; as 48 Gated DeltaNet são lineares e não usam flash attention). Na prática, com flash attention ativo, o modelo sustenta ~50 tok/s em GPU de 24 GB com os 262.144 tokens — contra ~34 tok/s sem (medições de piszczek.pl em RTX PRO 4000 Blackwell).

Ollama vs llama.cpp: tem overhead?

Essa é a pergunta que mais aparece. A resposta curta: quase nenhum no decode, algum no prefill.

O Ollama usa o llama.cpp como backend de inferência para modelos GGUF — não é um motor paralelo, é o mesmo código C++ compilado. O que o Ollama adiciona por cima:

CamadaOverheadDetalhe
Inferência (llama.cpp)0%É o mesmo backend — decode bruto é idêntico
API REST (servidor)~1–3%Serialização JSON + HTTP; imperceptível em uso interativo
Gerenciamento de contexto~0,5%Cache de sessão e roteamento de requests
Build do GGUFVariávelO build GGUF pode diferir entre o Ollama Hub e o Unsloth — diferenças de desempenho são do quant, não do motor

Quando usar Ollama: quando você quer o modelo rodando em 5 minutos, com API nativa, gerenciamento de modelos, e não está no limite de milissegundos por token. É a escolha certa para 95% dos usuários.

Quando usar llama.cpp puro: quando você precisa de controle milimétrico — flags experimentais (--flash-attn, --no-flash-attn), múltiplos drafters, tuning de --batch-size para prefill, ou está montando um benchmark controlado. Também quando o Ollama não tem uma tag para o quant exato que você quer.

Dado real: no Strix Halo (128 GB RAM unificada), o Qwen3.8-27B Q4_K_M roda a ~17,3 tok/s tanto no Ollama quanto no llama.cpp — dentro da margem de erro de medição. O overhead é estatisticamente irrelevante para uso real.

Usando via API (OpenAI-compatible)

O servidor embutido do Ollama expõe uma API REST OpenAI-compatible na porta 11434. Isso significa que qualquer ferramenta que aceita OPENAI_API_KEY e OPENAI_BASE_URL pode apontar para o seu Ollama local:

# No seu app Python com openai SDK
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:11434/v1",
    api_key="ollama"  # qualquer valor, o Ollama não valida
)

response = client.chat.completions.create(
    model="qwen3.8:27b",
    messages=[{"role": "user", "content": "Escreva um poema sobre LLMs locais."}],
    temperature=1.0,
    top_p=0.95
)
print(response.choices[0].message.content)

Options extras (reasoning_effort, no_think):

# Via OpenAI SDK com extra_body
response = client.chat.completions.create(
    model="qwen3.8:27b",
    messages=[{"role": "user", "content": "Resolva 25 × 47 passo a passo."}],
    extra_body={
        "options": {
            "reasoning_effort": "high",
            "no_think": False
        }
    }
)

Para servidores que exigem um servidor dedicado com thread pool para concorrência, inicie o Ollama em modo servidor:

ollama serve

E faça as requisições para http://localhost:11434. O servidor gerencia fila de requests concorrentes automaticamente, com uma instância do modelo em GPU.

Perguntas frequentes

Ollama é recomendado para produção?

Depende do que você chama de produção. Para uso pessoal, agentes locais, equipes pequenas — sim, Ollama serve bem com sua API OpenAI-compatible e servidor embutido. Para dezenas de requests concorrentes, throughput máximo, prefix caching, os motores de serving dedicados (vLLM, SGLang) têm vantagem. Uma arquitetura comum: Ollama no dev/local, vLLM em produção.

Qual tag escolher para maximizar qualidade?

A hierarquia de qualidade acompanha a precisão: BF16 > Q8_0 > Q4_K_M. Na prática, entre Q4_K_M e BF16 a diferença em benchmarks de múltipla escolha é tipicamente <1% (MMLU, ARC, HellaSwag). A diferença real aparece em tarefas de raciocínio longo e geração criativa. Para 99% dos usos, o Q4_K_M (18 GB) é a escolha certa — e se couber na sua VRAM, o Q8_0 (30 GB) é o ponto doce.

Ollama no Mac é diferente do Ollama no Linux?

No Mac, o backend é MLX (Apple Silicon) em vez de CUDA/llama.cpp para as tags MLX (27b-mlx, 27b-mlx-bf16, etc.). As tags não-MLX (tipo :27b) rodam via llama.cpp no Mac também, mas com desempenho inferior ao MLX. Para melhor performance no Mac, use as tags MLX — elas usam a GPU e Neural Engine via Metal/MLX.

MTP no Ollama funciona com qualquer tag?

Não. O MTP só funciona com as tags que incluem a cabeça MTP no pacote — as que têm -mtp- no nome. A tag :latest e :27b não têm a cabeça MTP. Se você quiser MTP, use qwen3.8:27b-mtp-q4_K_M.

Como ver o Modelfile de um modelo já baixado?

ollama show --modelfile qwen3.8:27b

Qual o comando para listar modelos baixados?

ollama list

O Ollama suporta tool calling no Qwen3.8?

Sim, a biblioteca Ollama marca o qwen3.8 como tools — tool calling é suportado via API. O modelo usa o formato Qwen (JSON dentro de <tool_call>). Na API Python do Ollama, passe tools=[...] na chamada chat().

Ollama vs LM Studio: qual a diferença prática?

LM Studio é uma GUI nativa para desktop (macOS, Windows, Linux) que também usa llama.cpp como backend — conceitualmente similar ao Ollama. Diferenças: LM Studio tem interface gráfica com download de modelos embutido e descubra de builds GGUF; Ollama é linha de comando + API (mais adequado para integração com código e agentes). Ambos expõem API OpenAI-compatible. Para uso via terminal e agentes, Ollama é mais direto; para quem prefere interface visual, LM Studio. Veja nosso guia de quantização GGUF para escolher o build certo.
