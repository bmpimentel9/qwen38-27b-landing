Qwen3.8-27B no vLLM em produção: prefix caching, flags e bugs reais

O SGLang tem o guia de throughput; este é o guia do outro motor que a recipe oficial da Qwen recomenda. Comando base de produção com cada flag justificada, prefix caching no híbrido Mamba, MTP com aceitação medida por precisão — e os seis bugs abertos que vão te atingir quando o 3.8 vira infraestrutura, cada um com o workaround documentado na issue.

A resposta rápida

O comando mínimo de produção para o Qwen3.8-27B-FP8 no vLLM (GPU com tensor parallel, ex.: 4× 32 GB ou GB300):

vllm serve Qwen/Qwen3.8-27B-FP8 \
  --served-model-name qwen3.8-27b \
  --tensor-parallel-size 4 \
  --max-model-len 262144 \
  --kv-cache-dtype fp8 \
  --enable-prefix-caching \
  --reasoning-parser qwen3 \
  --enable-auto-tool-choice \
  --tool-call-parser qwen3_coder

Em uma única RTX 5090 de 32 GB, o checkpoint muda para NVFP4 com --enforce-eager e contexto 32K — detalhes e a tabela por hardware na seção Hardware verificado. A versão de referência deste guia é a vLLM 0.27.1, a estável mais recente no PyPI em 20/08/2026.

Por que vLLM para o Qwen3.8-27B (e quando não)

O model card oficial do Qwen3.8-27B lista três engines de produção: SGLang, vLLM e TokenSpeed — cada uma com recipe própria. O vLLM tem três diferenciais para quem já roda o 3.8 em produção ou está escolhendo o stack:

  • Recipe oficial por hardware (recipes.vllm.ai): comandos validados em GB300, 2× RTX 5090, 1× RTX 5090 e Ascend 950PR — com tamanho de pool de KV e aceitação de MTP medidos por precisão.
  • Caminho em hardware fora da NVIDIA: recipe dedicada em Ascend 950PR com INT8 ModelSlim e MTP funcionando (64 tok/s single-stream); suporte ROCm habilitado desde julho (#50068).
  • Sampling de frames de vídeo por request via extra_body (fps, do_sample_frames) — a recipe oficial nota que este recurso hoje só existe no vLLM.

Quando não: se o alvo é o máximo throughput single-GPU em Blackwell, os números divulgados da equipe Qwen/SGLang (206,1 tok/s na RTX 5090) seguem na frente — nosso guia SGLang + FP8 cobre esse caminho. E em GPU de 24 GB sem Blackwell, o caminho prático continua sendo GGUF via llama.cpp (veja o mapa de quantizações).

O que o híbrido 48+16 muda no serving

O Qwen3.8-27B não é um transformer convencional, e isso muda três coisas na hora de servir:

  • 48 das 64 camadas são linear attention (Gated DeltaNet, full_attention_interval: 4 no config.json): o estado recorrente tem tamanho fixo — o KV cache "caro" existe só nas 16 camadas full-attention. É por isso que o mesmo hardware comporta muito mais contexto do que um denso 27B tradicional.
  • Prefill dominado por kernels Triton/FLA: a recipe mostra o caminho GDN prefill kernel no boot. É código novo, com bugs novos — dois dos seis da tabela de bugs estão exatamente aí (captura de CUDA graph e alinhamento Mamba no prefix caching).
  • Prefix caching tem que alinhar estado Mamba com blocos KV: em vez de só cachear K/V, o scheduler precisa casar o estado recorrente com as fronteiras de bloco. É onde vive o bug multimodal (#52583) — e é por isso que o suporte amadureceu ao longo da 0.27.x, com o commit que liga o prefix cache do caminho Mamba por padrão (#50991) entrando no main após o corte da 0.27.1.
Consequência prática: em produção, passe --enable-prefix-caching explícito mesmo que o default global seja True — você documenta a intenção e fica imune a mudanças de default entre minor versions do caminho híbrido.

Passo 1 — Instalar (pip, uv ou Docker)

A recipe oficial pede vLLM 0.17.0 no mínimo e transformers >= 5.8.0 (o requisito existe por causa do processor Qwen3-VL, não do model loader). A estável mais recente é a 0.27.1, publicada em 11/08/2026:

# ambiente limpo, Python 3.10+, CUDA 12.x
pip install --upgrade pip
pip install "vllm==0.27.1" "transformers>=5.8.0"

# ou com uv (mais rápido)
uv pip install "vllm==0.27.1"

# ou Docker (imagem usada nos relatos de produção da comunidade)
docker run --gpus all -p 8000:8000 \
  -v ~/.cache/huggingface:/root/.cache/huggingface \
  vllm/vllm-openai:latest \
  --model Qwen/Qwen3.8-27B-FP8 \
  --max-model-len 262144 --kv-cache-dtype fp8
Não persiga a "0.27.2": essa versão não existe — a sequência no PyPI vai de 0.27.0 (10/08) a 0.27.1 (11/08), e o que vem depois é 0.28.0rc1. Tutoriais e guias que exigem "vLLM ≥ 0.27.2" para o Qwen3.8-27B estão com a versão errada (este portal corrigiu as próprias páginas — a exigência real da recipe oficial é 0.17.0+).

Passo 2 — O servidor de produção, flag por flag

O comando base da seção "resposta rápida", destrinchado. Os defaults do vLLM são bons; estas são as flags que fazem o setup de produção para o 3.8:

FlagPor quê
--reasoning-parser qwen3Não é opcional na prática (texto da recipe oficial): o chat template abre todo turno com <think> — sem o parser, o raciocínio inteiro cai em message.content e um orçamento de 2.048 tokens se esgota antes da resposta começar.
--tool-call-parser qwen3_coder
--enable-auto-tool-choice		Tool calls no formato do modelo. Par obrigatório para agentes — e o ponto onde mora o bug #52564 (respostas vazias); se o seu caso de uso é agêntico, teste tool calls antes de promover o build.
--max-model-len 262144Contexto nativo do modelo (max_position_embeddings no config.json). Reduzir libera VRAM para mais KV; estender a 1M exige override (Passo 5).
--kv-cache-dtype fp8KV em FP8 quase dobra o pool. Na recipe 1× 5090: 91.022 tokens de KV com fp8 contra 76.458 em bf16 — "uma escolha, não um requisito", nas palavras da recipe. Evite turboquant_* com MTP (bug #52475).
--enable-prefix-cachingExplícito no híbrido Mamba — veja o Passo 3.
--served-model-nameNome estável na API, desacoplado do caminho do checkpoint (que você vai trocar entre FP8/NVFP4 ao ajustar hardware).
--tensor-parallel-size1 para NVFP4 em Blackwell 24–32 GB; 2 para 2× 5090; 4 para FP8 num tray GB300 ou 4× 32 GB.

Teste imediato após o boot (espera ~1–3 min de captura de CUDA graphs, se não estiver em eager):

curl http://localhost:8000/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model": "qwen3.8-27b",
    "messages": [{"role": "user", "content": "Três primos acima de 100."}],
    "temperature": 1.0, "top_p": 0.95, "max_tokens": 2048,
    "chat_template_kwargs": {"enable_thinking": false}
  }'

temperature 1.0 / top_p 0.95 / top_k 20 são os valores de fábrica do generation_config.json do modelo — mantenha-os salvo quando tiver motivo para não mantê-los.

Passo 3 — Prefix caching no híbrido Mamba

Automatic Prefix Caching (APC) reutiliza o KV de requisições que compartilham prefixo. O ganho é concentrado em duas cargas — exatamente as duas da documentação oficial:

  • Multi-turn / agentes: o histórico da conversa é prefixo repetido a cada turno; com APC, ele é computado uma vez.
  • RAG sobre documento fixo: o mesmo manual/relatório consultado com perguntas diferentes paga o prefill só na primeira.

O que o APC não faz: acelerar o decode. Ele corta o prefill de prefixos repetidos — se a sua carga responde longo ou não repete prefixo, ele não entrega nada (e ainda cria a janela para o bug multimodal abaixo).

O estado em 0.27.1

  • O default global é enable_prefix_caching = True no código da 0.27.1 (vllm/config/cache.py).
  • Para o caminho Mamba/híbrido especificamente, o scheduler ganhou alinhamento de estado Mamba antes dos caps de encoder no PR #51603 (merged 10/08, apontado pelos maintainers como fix a testar na #52583), e o prefix cache default do caminho Mamba (#50991) entrou no main após o corte da 0.27.1.
  • Em produção com o 3.8: flag explícita --enable-prefix-caching, e a armadilha multimodal abaixo mapeada.
Armadilha multimodal (#52583, aberta em 17/08): com prefix caching ligado, requisições com imagens grandes/triplas de vídeo travam o prefill indefinidamente — o alinhamento de hash do APC vira gargalo de CPU no caminho multimodal. Relatado em H20, vLLM 0.16/0.21, Qwen3.8 híbrido. Workaround: --no-enable-prefix-caching resolve por completo (relato do autor da issue). Se a sua carga é texto puro, o APC segue recomendado.

Como validar que o APC está trabalhando: dispare duas requisições idênticas de prefixo longo e compare o TTFT da segunda, ou acompanhe as métricas de cache hit no endpoint /metrics (gauge de blocos hit/miss do prefix cache).

Passo 4 — MTP: speculative decoding e a métrica que prova que funciona

O checkpoint traz a cabeça MTP treinada pela Qwen (mtp_num_hidden_layers: 1 no config.json) — não há nada para baixar além do modelo. Liga com uma flag:

--speculative-config '{"method":"mtp","num_speculative_tokens":3}'

A aceitação medida pela recipe oficial a 262.144 de contexto, por precisão:

Precisão (TP2, 2× RTX 5090)KV tokensPesos/GPUAceitação MTP
FP8377.45614,28 GiB0,771
NVFP4 (Inferact, W4A4 uniforme)445.87512,02 GiB0,897
NVFP4 (unsloth, mista FP8+4-bit)920.51710,64 GiB0,788

As duas builds NVFP4 não são intercambiáveis em placas de 32 GB: a unsloth (FP8 channel-wise junto dos grupos 4-bit) deixa ~2× o KV; a Inferact (W4A4 uniforme) tem o melhor rascunho. Ambas servem corretamente.

Como saber se o drafter está vivo: acompanhe vllm:spec_decode_num_accepted_tokens_total e vllm:spec_decode_num_draft_tokens_total em /metrics. A recipe oficial é categórica: throughput sozinho não distingue um drafter funcionando de um que carregou e foi ignorado. Meça antes de tunar num_speculative_tokens.
Duas armadilhas do MTP: (1) com KV cache turboquant_4bit/3bit_nc em sm_120 (RTX 5090), o MTP degenera em repetição silenciosa — ~230 repetições do mesmo token, apenas em prompts longos, 12/12 runs; com KV fp8, limpo (#52475). (2) num_speculative_tokens: 1 com turboquant não degenera — mata o engine com EngineDeadError. Em resumo: MTP + KV fp8 é o par testado; MTP + turboquant não.

Passo 5 — Contexto 262K nativo e 1M com override

Os 262.144 tokens vêm de fábrica (max_position_embeddings no config.json — a conta de por que isso cabe está no nosso guia do contexto 256K em 24 GB). Para 1M em vLLM, o override é aninhado em text_config — diferente do Qwen3.8-2.4T, que o recebe plano:

vllm serve Qwen/Qwen3.8-27B \
  --max-model-len 1010000 \
  --hf-overrides '{"text_config": {"max_position_embeddings": 1010000}}'

O trade-off é direto: cada token de contexto consome pool de KV. Na recipe NVFP4/unsloth a 262K o pool chega a 920.517 tokens — o bastante para ~3,5 sequências completas de 262K simultâneas, ou 1 de 1M com troco.

Os 6 bugs conhecidos (e os workarounds)

Situação em 20/08/2026, todas as issues abertas no repositório do vLLM — este é o mapa que falta nos tutoriais "sobe e roda":

SintomaCausaWorkaroundFonte
Startup trava sem erro após os kernels FLA/FLASHINFER (TP4 em Ampere) Captura de CUDA graph no caminho híbrido; não é autotuning lento --enforce-eager #52682
Prefill trava indefinidamente com imagens grandes + prefix caching Alinhamento de hash do APC no prefill multimodal (CPU-bound) --no-enable-prefix-caching; testar PR #51603+ #52583
Tool calls voltam vazias com FP8 (respostas "(empty)") Auto-stop do parser de tool call no FP8 Sem fix estável — reproduza seu fluxo agêntico antes de promover o build #52564
Resposta repete um token ~230× — só em prompts ~8K; curtos respondem certo MTP + KV turboquant_4bit/3bit_nc em sm_120 KV fp8 (12/12 runs limpos); nunca num_speculative_tokens:1 com turboquant (mata o engine) #52475
Checkpoint MXFP4 não carrega em GPU NVIDIA Implementação MXFP4 sem linear method em NVIDIA Usar NVFP4 Recipe oficial (Troubleshooting)
Boot falha com --language-model-only (modo texto sem vision tower) CUDA graph do encoder criado sem a vision tower PR de fix #52734 aberto; enquanto isso, servir com a torre (padrão) #52734

Padrão útil de leitura: quatro dos seis se resolvem com uma decisão de flag (--enforce-eager, --no-enable-prefix-caching, KV fp8, NVFP4). Nenhum deles derruba o servidor de forma ruidosa — travam em silêncio ou corrompem a saída, que é o pior modo de falha em produção. Por isso a seção de validação importa tanto quanto a de instalação.

Cliente: thinking, sampling e vídeo por request

O thinking vem ligado de fábrica em modo xhigh. Controle por requisição via chat_template_kwargs:

{"enable_thinking": false}   // sem raciocínio: resposta direta
{"reasoning_effort": "low"}  // thinking adaptativo: xhigh (default) | medium | low

Ou server-wide com --default-chat-template-kwargs '{"enable_thinking": false}' — o retângro de latência que isso corta (2,18 s → 0,18 s até a primeira palavra no mesmo setup) está no nosso guia de configuração de reasoning.

Para vídeo, o vLLM é hoje a única engine com sampling de frames por request (a recipe oficial destaca): suba o servidor com --media-io-kwargs '{"video": {"num_frames": -1}}' e controle por chamada via extra_body — fps (default 2) e do_sample_frames. Para visão/OCR no caminho GGUF, o guia é o de visão e vídeo local.

vLLM ou SGLang?

Mesmo checkpoint FP8, cabeça MTP embutida nos dois, parsers qwen3 nos dois. A decisão prática:

O comparativo completo do outro caminho está no guia SGLang + FP8.

Perguntas frequentes

Como rodar o Qwen3.8-27B no vLLM?

vllm serve Qwen/Qwen3.8-27B-FP8 --max-model-len 262144 --kv-cache-dtype fp8 --enable-prefix-caching --reasoning-parser qwen3 --enable-auto-tool-choice --tool-call-parser qwen3_coder. Em GPU única de 32 GB, NVFP4 com --enforce-eager e contexto 32K; o FP8 completo pede tensor parallel (recipe oficial: TP4 no GB300, TP2 em 2× 5090).

Qual versão do vLLM preciso para o Qwen3.8-27B?

A recipe oficial pede vLLM 0.17.0+ e transformers ≥ 5.8.0. A estável mais recente é a 0.27.1 (11/08/2026, PyPI). A "0.27.2" citada em alguns tutoriais não existe — depois da 0.27.1 vem a 0.28.0rc1.

O prefix caching está ligado por padrão no vLLM?

Sim — enable_prefix_caching é True na 0.27.1 (código-fonte). Para o caminho Mamba do 3.8, o default específico (#50991) entrou no main após o corte da 0.27.1: em produção, passe a flag explícita. E lembre: APC acelera prefill de prefixos repetidos (multi-turn, RAG), nunca o decode.

vLLM ou SGLang para o Qwen3.8-27B?

Mesmo checkpoint e MTP embutido nos dois. SGLang lidera os números de throughput divulgados (206,1 tok/s na 5090); vLLM tem recipe oficial por hardware, caminho Ascend/ROCm e o sampling de frames de vídeo por request. Detalhes na seção vLLM ou SGLang acima.

Quanto de VRAM precisa o Qwen3.8-27B no vLLM?

O FP8 pesa 30,89 GB (medição via HF API): 262K completo pede TP4 ou TP2+NVFP4. Na 1× RTX 5090 de 32 GB, NVFP4 só com --enforce-eager e 32K de contexto (91.022 tokens de KV com KV fp8). Em 24 GB, o caminho é GGUF/llama.cpp.

Quais bugs conhecidos afetam o Qwen3.8-27B no vLLM?

Seis em 20/08/2026: hang na captura de CUDA graph em TP4/Ampere (#52682, fix --enforce-eager), prefill travado com APC + imagens grandes (#52583), tool calls vazias no FP8 (#52564), repetição silenciosa com MTP + KV turboquant (#52475), MXFP4 que não carrega em NVIDIA e boot falhando com --language-model-only (#52734).
